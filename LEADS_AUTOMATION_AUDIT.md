# LEADS_AUTOMATION_AUDIT.md — Phase 1 Audit for the Leads Ecosystem / Agentic AI Runtime Redesign

**Audit date:** 2026-08-18 · **Branch:** `claude/studio-ui-ux-rating-ieee3s` · **Scope:** read-only, static code reading only — no route was invoked, no data modified, no live phone numbers/WhatsApp numbers/AI calls made during this audit.

This audit answers the spec's own Section 35/37 mandate ("EXISTING PROJECT FIRST — inspect before coding") for the specific slice of work described: Leads lifecycle, 10 AI agents, Tool Registry, Automation Orchestrator, Communication Service, backend Scheduler, Observability, Security, AI Provider abstraction, future n8n pluggability.

Two prior audits already exist at the repo root from an earlier, broader session (`PROJECT_AUDIT.md`, `ARCHITECTURE_MAP.md`, `SCHEMA_SNAPSHOT.md`, `TECH_DEBT.md`, dated 2026-08-17, written against a different/larger "AI Workforce OS" spec). This document is scoped tightly to the Leads/Agentic-AI-Runtime spec and independently re-verifies every claim against the actual files in this repo rather than citing the older documents blind — but their findings agree with what's below wherever they overlap, and are cited where useful.

---

## 1. Executive Summary

A meaningful fraction of the new spec's ambition already exists in real, working, narrow form — but almost none of it exists as the *general, reusable infrastructure* the spec describes. Concretely: there is a real, working AI provider abstraction with three interchangeable providers and honest "not configured" failure (`backend/services/aiProvider.js`), a real WhatsApp Cloud API integration and a real Brevo email integration (not stubs), a real rule-based deterministic lead-scoring engine, a real cross-module "Lead 360" aggregation with AI-synthesized narrative, and a real (if narrow) "Next Best Action" endpoint already living in `cockpit.js`. These are legitimate seeds for several of the spec's 10 agents and for its Lead Intelligence Engine.

What does **not** exist: any state-machine enforcement on lead stage (it is a free-text column matched loosely against a separate, unrelated `pipeline_stages` table); a Tool Registry with permissions/schemas/audit logging; risk-tiered agent permissions or a human-approval queue; an event bus with retry/backoff/idempotency/dead-letter states (the existing `automationEngine.js` is a simple, synchronous, best-effort in-process trigger→action dispatcher with none of these); a backend Scheduler in the sense of an in-process job runner (the one real "scheduled" capability — WhatsApp scheduled sends — is driven by an *external* GitHub Actions cron hitting an HTTP endpoint, which is at least not browser-timer-dependent, but is also not a general-purpose scheduler any other feature can register jobs with); an Automation Dashboard beyond a single trigger/action rule-list screen; and any AI-cost/usage tracking. Webhook signature validation is real for Razorpay payments (HMAC verify) but **absent** for both WhatsApp and Facebook Lead Ads inbound webhooks — those only check a GET-time verify token, not per-message authenticity, which is a concrete security gap the spec's "webhook signature validation" requirement should close.

Net verdict: this is a mature, feature-rich CRM (61 backend route files, ~18 services, 66 Flutter screens, 785 real leads across 4 tenants in production) that already automates a handful of narrow workflows well — but the spec's "dual MANUAL/AGENTIC-AUTO system with 10 scoped agents, tool registry, risk tiers, and a durable orchestrator" is a genuinely new layer to build. The right posture, per the spec's own instruction, is to **extend** `automationEngine.js` and `aiProvider.js` rather than replace them, while building the state machine, tool registry, and durable orchestration as new, additive infrastructure that existing routes opt into gradually.

## 2. Existing Lead Lifecycle

**Column:** `leads.stage` — plain `TEXT`, no `CHECK` constraint, no enum type, no dedicated migration defining it (per `SCHEMA_SNAPSHOT.md`'s live schema dump: `leads` has `stage` alongside `source_category`, `engagement_trend`, `deleted_at`/`deleted_by` for soft-delete).

**Values actually used in code** (grepped across every route/service file that references `stage =` or `'stage_...'`):
- `New` — default on creation (`leadAdsWebhook.js`, `capture.js` default_stage fallback, `leadsExcelV2.js` import default)
- `Contacted` — referenced only in `leadScoring.js`'s `stage_Contacted` weight key
- `Counseling` — referenced only in `leadScoring.js`'s `stage_Counseling` weight key and `meetings.js`'s meeting-type list
- `Admission` — referenced in `leads.js` referral conversion queries, `leadScoring.js` weight, `cockpit.js`/`scoring.js` active-lead exclusion logic implicitly via `Closed`
- `Closed` — used to exclude "inactive" leads in `scoring.js` (`stage NOT IN ('Closed','Lost')`), `cockpit.js` send-queue, `students.js` (marks a lead `Closed` on enrollment), `performance.js`
- `Lost` — same exclusion pattern, plus `leadScoring.js`'s `stage_Lost: -30` weight

**Critically: there is no canonical, enforced list of stage values anywhere in the backend.** The actual *display* stage names a tenant sees and filters by come from a **separate table**, `pipeline_stages` (`id, tenant_id, name, position, color`), managed via `backend/routes/pipelineStages.js` — fully tenant-customizable (create/rename/reorder/delete stage names). `leads.stage` is just a string that's expected to match one of those names, but nothing enforces the match. `pipelineStages.js`'s own DELETE handler comment states this plainly: *"a lead's `stage` field is just text — deleting a stage definition doesn't retroactively move leads."* The mobile `leads_list_screen.dart` filter chips are literally built by iterating `pipeline_stages` rows (`s['name']`) and passing that string straight into `GET /leads?stage=`.

**Side-state columns that exist informally, not as part of the state machine:**
- `deleted_at`/`deleted_by` — soft-delete (Trash), fully separate from `stage`.
- `engagement_trend` — computed by `services/engagementTrend.js`, values like `rising/steady/cooling/cold`, stored back onto the lead row by `cockpit.js`. This is functionally adjacent to the spec's proposed `DORMANT`/`REACTIVATION` side-states but is a parallel, uncoupled signal, not a stage value.
- No `NOT_INTERESTED`, `ON_HOLD`, `DOCUMENT_PENDING`, `PAYMENT_PENDING`, `COMMITMENT`, `ADMISSION_CONFIRMED`, or `CONTACT_PENDING`/`ENGAGED`/`QUALIFIED` values exist anywhere — those distinctions currently live, if at all, as *derived* facts computed on the fly by `lead360.js` (fee/document/visa/consent alerts) rather than as first-class stage values.

**Comparison to the spec's proposed state machine** (`NEW → CONTACT_PENDING → CONTACTED → ENGAGED → QUALIFIED → COUNSELLING → APPLICATION → DOCUMENT_PENDING → OFFER/COMMITMENT → PAYMENT_PENDING → ADMISSION_CONFIRMED` + `NOT_INTERESTED/LOST/DORMANT/REACTIVATION/ON_HOLD`):

| Spec state | Current equivalent | Gap |
|---|---|---|
| `NEW` | `stage = 'New'` | exists, same name |
| `CONTACT_PENDING` / `CONTACTED` | no distinct value — inferred from `communications` row count / `last_contacted_at` | not a stage value; would need new enum entries or a derived-field mapping |
| `ENGAGED` / `QUALIFIED` | `engagement_trend` + `leadScoring.js` temperature (`hot/warm/cold`) approximate this but are separate fields, not stage | conceptually adjacent, structurally disjoint |
| `COUNSELLING` | `stage = 'Counseling'` (tenant pipeline stage, not universal) | naming drift (`Counselling` vs `Counseling`) + tenant-configurable, not fixed |
| `APPLICATION` | `admission_applications` table existing (separate entity, not a lead stage) | data exists, but as a child table not a stage transition |
| `DOCUMENT_PENDING` | `documents.status IN ('pending','rejected')` computed live by `lead360.js` | exists as a *derived alert*, not a lead stage |
| `OFFER`/`COMMITMENT` | `offers` table + `offers.status` | exists as a child entity, not a lead stage |
| `PAYMENT_PENDING` | `fee_payments.status IN ('pending','overdue')` | exists as a *derived alert* on a child table, not a lead stage |
| `ADMISSION_CONFIRMED` | `stage = 'Admission'` (approximate) | naming drift; also `admission_applications.application_status = 'Accepted'` is the more precise signal and lives on a different table |
| `NOT_INTERESTED`/`LOST`/`DORMANT`/`REACTIVATION`/`ON_HOLD` | only `Lost` exists as a stage value; `DORMANT` most closely maps to `engagement_trend = 'cold'` | four of five side-states have zero equivalent |

**Renaming/mapping needed for Phase 2:** the new state machine cannot simply overwrite `leads.stage` in place without a migration plan, because (a) 785 live production leads already hold values like `New`/`Contacted`/`Counseling`/`Admission`/`Closed`/`Lost` plus whatever free-text a tenant typed via their custom `pipeline_stages`, and (b) the mobile app's filter chips are generated dynamically from `pipeline_stages.name`, so a hardcoded new enum would break that screen unless `pipeline_stages` is migrated in lockstep or the two concepts are explicitly reconciled (recommend: keep `pipeline_stages` as the tenant-facing *display* label and introduce a new, separate, enforced `lifecycle_status` enum column that the spec's state machine actually drives — see §12).

## 3. Existing Automation Infrastructure

**Files:** `backend/routes/automations.js` (58 lines) + `backend/services/automationEngine.js` (45 lines). Read in full.

**Trigger model:** a fixed, hardcoded whitelist of five trigger event names: `VALID_TRIGGERS = ['lead.created', 'lead.stage_changed', 'document.rejected', 'offer.given', 'fee.paid']`. Each is fired by an explicit `await fireEvent('event.name', context)` call placed inline in the relevant route handler — confirmed call sites: `leads.js` (`lead.created` on POST /leads, `lead.stage_changed` on PATCH /leads/:id when `stage` is in the body), `leadAdsWebhook.js` (`lead.created`, fire-and-forget with `.catch()`), `documents.js` (`document.rejected` when a document's status is PATCHed to rejected), `cockpit.js` (`offer.given` on POST /offers, `fee.paid` on POST /:leadId/mark-fee-paid). This is **purely reactive to in-process API calls** — there is no polling, no cron, no external event source feeding it (except indirectly, since a webhook handler like `leadAdsWebhook.js` is itself an HTTP endpoint that then calls `fireEvent`).

**Action model:** exactly two supported actions, also hardcoded: `VALID_ACTIONS = ['create_reminder', 'create_notification']`. A rule optionally has one `condition_field`/`condition_value` exact-match filter (`if (context[rule.condition_field] !== rule.condition_value) continue;` — no operators, no AND/OR, no ranges). `action_config` is a JSON blob interpreted differently per action type (`{title, offset_days, assigned_to}` for reminders; `{title, body}` for notifications).

**Execution model:** `fireEvent()` runs entirely **synchronously and in-process**, inside the same request/response cycle as whatever triggered it (with two call sites choosing to fire-and-forget via `.catch()` for non-critical paths). It queries `automation_rules` for matching enabled rules, loops over them, and does direct `INSERT`s for each match. There is:
- **No retry/backoff** — a failed `INSERT` (e.g., a transient DB blip) throws and is either swallowed by the caller's `.catch()` (silently dropped, logged to console only) or propagates and potentially 500s the parent request, depending on the call site.
- **No idempotency** — confirmed by repo-wide grep: zero occurrences of "idempotenc" anywhere in `backend/`. Calling `fireEvent('lead.created', ...)` twice for the same lead (e.g., a client retry after a timeout) creates the reminder/notification twice, with nothing to detect or dedupe it.
- **No dead-letter concept** — confirmed by repo-wide grep: zero occurrences of "dead_letter"/"dead-letter" anywhere. A failed action simply never happened; there is no persisted failure record to inspect, retry, or route to a human queue.
- **No audit trail of automation executions** — `automation_rules` stores the *rule definitions*, but there is no `automation_runs`/`automation_log` table recording "rule X fired for lead Y at time Z, action succeeded/failed." (`backend/routes/audit.js` covers communications/documents/admissions/fees only — automation executions are not one of its four `ALL_TYPES`.)
- **Event-driven, not polling** — worth stating clearly since it's a genuine strength: this is real synchronous pub-sub-shaped code (a `fireEvent` call is effectively "publish," and the DB query for matching enabled rules is "find subscribers"), not a polling loop scanning for state changes. That part of the design direction is sound and worth keeping.

**UI:** Exactly one mobile screen, `mobile/lib/screens/automations_screen.dart` (122 lines) — a flat list of rules with a name/trigger/action subtitle and an enabled/disabled `Switch`, plus a creation dialog limited to the same fixed trigger list and *only* the `create_reminder` action (the dialog never exposes `create_notification` as an option, even though the backend supports it). There is no dashboard, no execution history view, no retry/failure surfacing, no condition-builder beyond the single-field exact-match the backend allows.

**Verdict — EXTEND, not replace, but only as the reactive-trigger half of a larger system.** `fireEvent()`'s core shape (rule lookup → condition check → action dispatch) is a legitimate, working seed for the spec's trigger-matching logic, and its trigger events (`lead.created`, `lead.stage_changed`, etc.) are exactly the right *kind* of event names the new Automation Orchestrator needs — reuse the event vocabulary and the call-site instrumentation pattern (routes already know to fire events at the right moments). However, `fireEvent()` itself cannot become the durable orchestrator described in the spec (idempotency keys, retry/backoff, dead-letter states, human approval queue) without fundamentally rearchitecting its execution model — it would need to write to a durable job/execution table *first*, then process asynchronously with retry logic, rather than doing direct synchronous side-effects inline. The pragmatic path: keep `fireEvent()`'s trigger-matching/condition-filtering logic as the "what should run" layer, but replace its "run it directly and forget" execution tail with an enqueue-to-a-durable-table step that a new orchestrator processes — additive, not a rewrite of the whole file.

## 4. Existing AI Infrastructure

**`backend/services/aiProvider.js` (134 lines) — REAL, genuinely wired to live LLM APIs, not a stub.** Confirmed: imports the real `@anthropic-ai/sdk` package (present in `backend/package.json` dependencies), calls `client.messages.create()` against Claude directly for the `claude` provider, and does real authenticated `fetch()` calls against `generativelanguage.googleapis.com` (Gemini) and `openrouter.ai/api/v1/chat/completions` (OpenRouter) for the other two. Provider selection is a single `AI_PROVIDER` env var; every feature in the app calls through one shared `generateText()`/`generateJson()` pair, so this genuinely is a working provider-abstraction layer already — the closest existing thing to the spec's "AI Model Provider abstraction (OpenAI/Anthropic/Gemini interchangeable)." Gaps versus the spec: no OpenAI provider (only Claude/Gemini/OpenRouter — OpenRouter can reach OpenAI models but that's indirect, not a first-class `openai` provider key), no per-tenant provider override (one env var for the whole deployment), no per-call/per-tenant cost or token-usage tracking, and **no deterministic-fallback wiring at the `aiProvider.js` level itself** — `generateText()` throws a clear "not configured" error when a key is missing rather than silently falling back; deterministic fallback is instead implemented *per-caller*, inconsistently (see below).

**Deterministic-fallback pattern — exists, but ad hoc, not centralized.** Three different fallback postures were found across callers of `aiProvider.js`:
1. `smartTriage.js`'s `triageMessage()` — genuine deterministic fallback: if `generateJson()` throws (no key, or call failed), it catches and falls back to sending the matched Knowledge Base article's raw text verbatim, never inventing an answer. This is exactly the spec's "never fabricate, fall back to deterministic rules" pattern, done correctly, in one place.
2. `ai.js`'s routes (`analyze-lead`, `generate-theme`, `restyle-section`, etc.) and `cockpit.js`'s AI routes — **no fallback at all**: a missing key or failed call returns a `502` with the raw error message to the client. Fine for a human-facing "AI feature is down" UI, but not compatible with an agent that's supposed to degrade gracefully to rule-based logic.
3. `leadScoring.js` — not AI-based at all; **fully deterministic by design** (see below), so it never needs a fallback because it never calls an LLM in the first place.

**`backend/services/aiAnalysis.js` (35 lines) — real, single-purpose.** `analyzeLead(lead, communications)` builds one prompt from a lead's full interaction history and asks for a structured JSON verdict (`summary`, `sentiment`, `buying_intent`, `risk_flags`, `suggested_next_action`, `suggested_whatsapp_reply`). This is a legitimate, narrow seed for the spec's **Qualification Agent** or **Calling Intelligence Agent** — it already produces buying-intent classification and a suggested next action, just not wrapped in any agent/tool/permission framework.

**`backend/services/leadScoring.js` (179 lines) — REAL but fully rule-based/deterministic, zero AI cost, explainable by design.** A transparent weighted-signal scorer (phone/email/parent-contact presence, outreach/reply counts, contact recency, meeting attendance, document/payment/application counts, referral source, overdue-followup penalty, current stage) producing a 0–100 score plus a `hot`/`warm`/`cold` temperature and a signed, human-readable list of contributing signals. Weights and hot/warm thresholds are tenant-configurable via `scoring_config` (managed through `backend/routes/scoring.js`, including a `/config/preview` endpoint that shows the effect of a proposed weight change across the tenant's whole lead base before committing). **This is the single best existing seed for the spec's Lead Intelligence Engine's `score`/`confidence`/`explanation` fields** — it already produces exactly that shape (score + signals-as-explanation), just under a different name and without a persisted per-lead score history.

**`backend/services/smartTriage.js` (106 lines) — REAL, narrow, and a genuinely good existing agent pattern to copy.** Answers inbound WhatsApp messages by keyword-matching against `knowledge_articles`, refining the match with an AI-drafted reply *grounded only in the matched article's text* when a provider is configured, and explicitly escalating to a human notification (never guessing) when confidence is low or no AI is configured. This is the closest existing thing in the codebase to the spec's "explicit prohibitions against fabricating unavailable capabilities" design goal for agents — worth studying as the house style for how a new agent should be written, not just reused as-is. It is currently gated behind `AUTO_TRIAGE_ENABLED` (off by default) and only wired into the WhatsApp inbound webhook path, not a general capability other channels can call.

**`backend/routes/predictions.js` (92 lines) — REAL, fully deterministic, zero AI calls.** Ranks colleges for a lead using the tenant's own historical `admission_applications` outcome data (offer rate, confidence bucketed by sample size: `no data`/`low`/`moderate`/`high`). No LLM involved at all — pure SQL aggregation + arithmetic. A legitimate seed for a future **Counselling Agent**'s "which programs fit this lead" capability, but currently entirely disconnected from any lead-facing recommendation flow (it's a standalone endpoint, not surfaced in `lead360.js` or `cockpit.js`).

**`backend/services/lead360.js` (`buildLead360`, 262 lines) — REAL cross-module aggregation + AI synthesis, the single richest existing AI feature.** Reads fees, documents, applications, offers, visa, travel, consent, meetings, reminders, and communications for one lead in parallel, computes a prioritized, severity-ranked alert list (critical/warning/info) via pure deterministic logic, then sends the whole snapshot + already-computed alerts to the AI provider for one synthesized `headline`/`narrative`/`top_action`/`risk_level` verdict — explicitly instructed *not* to repeat the deterministic alerts verbatim but to reason across them. This is architecturally very close to what a **Lead Intelligence Engine** needs to look like, and its "compute the facts deterministically first, then let AI narrate/prioritize on top" split is exactly the safe pattern the spec wants (deterministic ground truth, AI as an explanatory layer, not the source of truth).

**`backend/routes/cockpit.js` — contains an already-real "Next Best Action" endpoint (`POST /cockpit/:leadId/next-best-action`) plus a personalized draft engine and send-queue.** This is a significant, previously-easy-to-miss finding: the spec's "Next Best Action engine" is not a blank slate — `cockpit.js` already reads a lead's full communication + offer history, computes a rule-based engagement trend (`services/engagementTrend.js`, not AI), and asks the AI provider for one structured recommendation (`recommended_channel`, `urgency`, `reasoning`, `talking_points`, `engagement_read`, `risk_flag`). It also has a **Content Library + personalized Draft Engine** (`POST /:leadId/draft` — AI picks 0-1 pieces of tenant content and writes a one-off message, explicitly avoiding "the same draft twice") and a **Send Queue** (`GET /send-queue/today` — leads needing follow-up because of staleness) with a human-in-the-loop confirm-send step (`POST /:leadId/confirm-send` — logs only, never sends automatically). This whole file is close in *spirit* to the spec's Follow-up/Nurture agents plus its Next Best Action engine, minus any of the formal agent/tool/risk-tier framework.

**Mapping existing AI code onto the spec's 10 proposed agents:**

| Spec agent | Existing reusable seed | State |
|---|---|---|
| Intake Agent | `leadAdsWebhook.js`, `capture.js` (public capture forms), `leadsImport*.js` | data ingestion exists; zero agent framing, zero AI involved today |
| Qualification Agent | `leadScoring.js` (deterministic) + `aiAnalysis.js`'s `buying_intent` field | strong deterministic seed; AI layer exists but separate, not fused |
| Calling Intelligence Agent | `calls.js`'s stats/best-time-to-call + `aiAnalysis.js` sentiment | real deterministic call analytics; no AI-during-call capability exists (no transcription/live-assist) |
| Follow-up Agent | `cockpit.js` Next Best Action + Send Queue | the single best-matched existing seed in the whole codebase |
| Nurture Agent | `cockpit.js` Content Library + Draft Engine | good seed; currently manual-trigger only, no autonomous cadence |
| Counselling Agent | `predictions.js` (college fit) + `journey.js` (visa/travel data) | data + logic exist, disconnected from any conversational/recommendation agent |
| Document Agent | `documents.js` (verify/reject workflow) + `journey.js` checklist cross-referencing | strong deterministic checklist-matching seed; zero AI involvement today |
| Payment/Commitment Agent | `fees.js` (installment plans, auto-reminders, auto-receipts) | strong deterministic seed; zero AI involvement, no agent framing |
| Admission Agent | `admissions.js` (application status tracking) | data model exists; purely CRUD today, no agent logic at all |
| Lead Recovery Agent | `engagementTrend.js` (`cooling`/`cold` detection) | the closest thing to a "detect at-risk/dormant" signal that exists; no recovery *action* logic yet |

## 5. Communication Channels — real vs stubbed

**WhatsApp — REAL, genuine Meta WhatsApp Business Cloud API integration.** `backend/services/whatsapp.js`'s `sendWhatsAppMessage()` does an authenticated POST to `https://graph.facebook.com/v20.0/{phoneNumberId}/messages`, requiring real `WHATSAPP_TOKEN` + `WHATSAPP_PHONE_NUMBER_ID` from a real Meta Business account. When not configured, every call site throws a clear "WhatsApp not configured yet" error rather than pretending to succeed — `whatsapp.js`'s `GET /whatsapp/status` route exists specifically so the mobile app can check configuration state and show/hide the paid-send UI honestly ("Never assume configured — check the actual env vars every time"). This is exactly the spec's "never fake integrations, show NOT_CONFIGURED" rule, already implemented as house style. Inbound handling (`whatsappWebhook.js`) is also real — it processes genuine Meta webhook payloads, matches by phone number, and logs to `communications`.

**Email — REAL, via Brevo's HTTP API (not raw SMTP).** `backend/services/email.js` explicitly documents *why* it's HTTP-based, not SMTP: Render's free tier blocks outbound SMTP ports, confirmed by a live test noted in the code comment. Supports two tiers: platform-default Brevo credentials, or a tenant's own encrypted Brevo API key for full white-label sending (`own_brevo_api_key_encrypted`, decrypted via `services/crypto.js`). Real, working, not stubbed.

**Calls — REAL data capture, but no telephony provider integration at all.** `calls.js` is a rich *call-logging* system (outcome tracking, auto-follow-up scheduling, connect-rate/best-time analytics) but there is no Twilio, Exotel, or any VoIP/PSTN calling API anywhere in the codebase — a "call" in this app is something a counselor makes on their own phone and then manually logs the outcome of. There is no automated outbound dialing, no call recording, no live transcription. `voiceNotes.js`/`voice_notes` table stores manually-recorded voice memos with an AI-generated summary/transcript field, but that's post-hoc note-taking, not a calling agent.

**Facebook/Instagram Lead Ads — REAL webhook ingestion**, structurally identical in rigor to the WhatsApp webhook (verify-token handshake + inbound POST processing, `services/facebookLeadAds.js` fetches full lead field details via the Graph API). `GET /lead-ads/status` follows the same honest "check the actual env vars" pattern as WhatsApp's status route.

**Payments — REAL, three genuine gateway integrations** (`backend/services/payments.js`): Razorpay (order creation + **HMAC signature verification** — the one place in the whole codebase with real webhook/payment signature validation), eSewa (signed form-POST per their documented v2 contract), Khalti (real initiate + lookup calls). All three require the tenant's own merchant credentials; none work with zero configuration, and none is faked.

**Conclusion for §5:** every communication and payment channel that exists is a real, documented, provider-specific integration with honest "not configured" failure — there is no fabricated/fake integration anywhere in this part of the codebase, which is a strong foundation to build the spec's agents on top of (an agent calling `sendWhatsAppMessage()` gets a real send or a real, clear failure, never a silent no-op). The one channel the spec implies but that has zero equivalent is voice/telephony automation (no outbound-calling agent capability, no IVR, no call transcription pipeline).

## 6. Security & Tenancy model

**Tenant isolation:** 100% application-code discipline via `tenant_id` header, verified end-to-end. Every route file defines its own local `tenantId(req)` helper reading `req.header('x-tenant-id') || 'demo-consultancy'`. As of `backend/middleware/auth.js`'s Phase-1/Phase-3 rollout (read in full — see below), a **valid JWT overwrites this header server-side** so an authenticated caller cannot spoof a different tenant by lying in the header; an *unauthenticated* caller (no token) still falls through to trusting the raw header value, which remains a real exposure for any endpoint not yet gated by `enforceAuth`. Per the pre-existing `SCHEMA_SNAPSHOT.md`, Postgres RLS is enabled on 54/56 tables but has **zero actual policies defined**, and the connection role has `BYPASSRLS` — meaning RLS provides **no real protection today**; the `WHERE tenant_id = ?` clause in each query is the only real isolation boundary, and it is applied consistently in every route file read for this audit (leads, documents, fees, admissions, journey, cockpit, compliance, etc. — no missing-clause cross-tenant leak was found in the files read, though a full 61-file grep-audit as `TECH_DEBT.md` recommends was out of scope here).

**Auth model (`backend/middleware/auth.js`, 162 lines, read in full):** a real, carefully-staged JWT rollout — `attachUser` (verifies `Authorization: Bearer` if present, sets `req.user`, overwrites `x-tenant-id` from the verified token — never merges, so an authenticated request can't lie about tenant); `enforceAuth` (global gate, mounted in `server.js`, rejecting any non-public-path request without `req.user`); an explicit, individually-justified `PUBLIC_PREFIXES` allowlist (health check, login/register/verify-email/accept-invite, public lead-capture forms, the no-login UPI payment page, inbound webhooks from Meta/lead-ads since third parties can't send a user JWT, the GitHub Actions cron endpoint, public short links); `requireRole(...roles)` for RBAC. **Role model in practice:** a free-text `role` column on `users`, observed values `admin`/`counselor`/`viewer` (3 roles, not the spec's richer risk-tiered agent-permission model), and — confirmed via prior `TECH_DEBT.md` finding, spot-checked here — `requireRole()` is a correctly-implemented function but called in very few route handlers app-wide, meaning most destructive/sensitive actions (bulk delete, settings changes, compliance erase) are gated only by "is there a valid token," not "is this role allowed to do this."

**Webhook signature validation — inconsistent, and the gap matters for the spec.** Confirmed by direct code reading:
- **Razorpay (payments):** real HMAC-SHA256 signature verification (`verifyRazorpaySignature()` in `services/payments.js`, called from `routes/payments.js`'s `/razorpay/verify`) — this is the one genuinely correct example in the codebase.
- **eSewa/Khalti:** outbound requests are signed (eSewa's form POST includes an HMAC `signature` field per their contract); inbound verification uses Khalti's server-to-server lookup API rather than a webhook signature, which is an acceptable alternate pattern for that gateway.
- **WhatsApp inbound webhook (`whatsappWebhook.js`):** only verifies Meta's one-time `hub.verify_token` handshake on `GET` (registration time). The `POST` handler that processes every actual inbound message **does not validate Meta's `X-Hub-Signature-256` header at all** — any request can be forged as an inbound WhatsApp message, including from a spoofed lead number, and will be logged into `communications` and (if `AUTO_TRIAGE_ENABLED`) can trigger a real automated AI reply.
- **Facebook/Instagram Lead Ads webhook (`leadAdsWebhook.js`):** identical gap — same GET-verify-token-only pattern, no per-request signature check on the `POST` handler that creates real leads.

This is a concrete, fixable gap directly relevant to the spec's "webhook signature validation" security requirement — both Meta webhooks need `X-Hub-Signature-256` HMAC verification added (using the tenant's/app's `WHATSAPP_APP_SECRET`) before they can be trusted as an autonomous agent's event source.

**Secrets management:** consistently environment-variable-based (`.env` locally, Render env vars in production) across every integration found — `ANTHROPIC_API_KEY`/`GEMINI_API_KEY`/`OPENROUTER_API_KEY`, `WHATSAPP_TOKEN`/`WHATSAPP_PHONE_NUMBER_ID`, `BREVO_API_KEY`, `RAZORPAY_KEY_ID`/`SECRET`, `ESEWA_MERCHANT_CODE`/`SECRET_KEY`, `KHALTI_LIVE_SECRET_KEY`, `JWT_SECRET`, `CRON_SECRET`, `WEBHOOK_VERIFY_TOKEN`, `LEAD_ADS_VERIFY_TOKEN`. No secrets-manager/vault integration (Vault, AWS Secrets Manager, etc.) — a flat convention, consistently applied, no evidence of hardcoded secrets in the files read. One tenant-level exception exists and is handled correctly: `tenants.own_brevo_api_key_encrypted` is genuinely encrypted at rest via `services/crypto.js`, not plaintext.

## 8. Missing Services

Zero existing equivalent for any of the following — these are genuinely new builds:

- **Tool Registry** with per-tool permission scoping, input/output schema validation, and per-call audit logging. Nothing in the codebase treats "send a WhatsApp message" or "create a fee record" as a discrete, permissioned, schema-validated *tool* an agent invokes — they're just plain function calls.
- **Risk-tiered agent permissions** (LOW/MEDIUM/HIGH) with HIGH requiring human approval. `requireRole()` gates *routes* by human user role; nothing gates *agent actions* by a risk tier, and there is no concept of an agent-initiated action being distinct from a human-initiated one at the data layer (no `initiated_by: 'human' | 'ai' | 'automation'` column found on any write path).
- **Human approval queue.** No table, no route, no UI screen for "an agent proposed X, a human must approve before it executes." `cockpit.js`'s `confirm-send` pattern is the closest analog (AI drafts, human taps send) but it's a bespoke one-off in that file, not a general queue any agent/action can enqueue into.
- **Durable event bus with retry/backoff/dead-letter.** `fireEvent()` is synchronous and best-effort only (§3). No job table, no `status: pending|running|succeeded|failed|dead_letter` column anywhere in the schema, no exponential-backoff retry logic found in any file.
- **Idempotency keys.** Confirmed absent by repo-wide grep — zero occurrences of "idempotenc" in `backend/`.
- **Backend Scheduler (in-process job runner).** The only scheduled-execution capability found (`whatsapp.js`'s `/process-scheduled`) is triggered by an *external* GitHub Actions cron every 15 minutes hitting a public HTTP endpoint — real, and importantly *not* dependent on the mobile app/browser being open, but it is a single-purpose endpoint for one feature (scheduled WhatsApp sends), not a general scheduler other agents/automations can register recurring or delayed jobs with. No `node-cron`, `bullmq`, `agenda`, or Redis appears in `backend/package.json`.
- **Automation Dashboard / Automation Center.** The mobile `automations_screen.dart` is a flat rule list with an on/off switch — no execution history, no failure surfacing, no per-rule run count/success-rate, no dead-letter inspection UI.
- **Next Best Action *engine*** in the spec's general sense (works across all 10 agents' domains). What exists (`cockpit.js`) is scoped to communication-channel recommendations only — it doesn't reason about document/payment/admission next-steps the way the spec's unified engine implies.
- **AI Model Provider abstraction covering non-text modalities** (image/video/embeddings) or **per-tenant AI cost/usage ledger.** `aiProvider.js` is text-only, one shared key per deployment, with no usage metering found anywhere.
- **`AutomationProvider` interface / `LocalAutomationEngine` / future `N8nAutomationEngine` plug point.** No abstraction layer exists above `automationEngine.js` today — it's called directly by name from route files, not through an interface a second implementation could satisfy. (Correctly, no n8n client/adapter exists either — consistent with the spec's "do not wire in n8n now" instruction; the gap is the *interface*, not the missing n8n piece itself.)
- **Structured/observability logging.** Every error path found in this audit uses plain `console.log`/`console.error` (e.g., `whatsappWebhook.js`, `leadAdsWebhook.js`, `smartTriage.js`) — no structured logger (pino/winston), no correlation/trace IDs, no log levels, nothing queryable beyond raw Render log tailing.
- **Lifecycle state machine enforcement.** No code anywhere validates that a stage transition is legal (e.g., nothing stops a PATCH from moving a lead directly from `New` to `Admission`); `leads.js`'s PATCH handler accepts any string for `stage` with zero validation against `pipeline_stages` or any enum.

## 9. Architecture Conflicts

- **"Not browser-timer-dependent" vs. the current scheduling reality.** The spec explicitly wants automation to not depend on client-side timers. The good news: the one real scheduled-execution path today (`/whatsapp/process-scheduled`) is *already* server-triggered by an external cron, not by the mobile app being open — so this specific worry is less severe than it might appear. The actual conflict is narrower: that cron endpoint is single-purpose (only processes `scheduled_messages`), so a new Automation Orchestrator needing its own recurring "check for due jobs" tick cannot simply reuse it — it either needs its own GitHub Actions cron entry (same external-trigger pattern, extended) or a real in-process scheduler, and either choice needs a decision, not silent assumption.
- **Free-text `stage` vs. a real state machine.** As detailed in §2, `leads.stage` has no enforcement today and is only loosely tied to a separate, tenant-mutable `pipeline_stages` table. A hard state-machine enum introduced without reconciling this dual-table reality will either (a) break the existing tenant-customizable pipeline-stage-naming feature the mobile app's Leads List screen depends on, or (b) be silently bypassable by any code path still writing raw strings to `stage` (multiple exist: `leadsExcelV2.js` import, `leadAdsWebhook.js`, `students.js`, direct PATCH from the mobile app). This needs an explicit reconciliation decision (see §12), not an in-place column redefinition.
- **Synchronous automation execution vs. a durable orchestrator.** `fireEvent()` runs inline in the request/response cycle of whatever triggered it. If the new orchestrator instead enqueues work for async processing, every existing call site (`leads.js`, `documents.js`, `cockpit.js`, `leadAdsWebhook.js`) needs to change from "await the side-effect now" to "enqueue and return" — a real, if mechanical, refactor across 4+ files, not a drop-in replacement.
- **Tool Registry / risk tiers vs. today's flat function-call model.** Every AI-touching route (`ai.js`, `cockpit.js`, `smartTriage.js`) calls services directly with no permission check beyond "is this user authenticated for this tenant." Introducing per-tool risk tiers and a human-approval gate means every one of these call sites needs to route through the new Tool Registry instead of calling `generateJson()`/`sendWhatsAppMessage()`/etc. directly — another real refactor, not additive-only.
- **Two different multi-tenant-simplification TODOs already on record for webhooks.** Both `whatsappWebhook.js` and `leadAdsWebhook.js` contain explicit code comments admitting they're "simplified to the demo tenant" because there's no real phone-number-to-tenant or Facebook-Page-to-tenant mapping yet. Any new agent that consumes these webhook events inherits this same simplification until it's fixed — worth flagging so the new Intake Agent doesn't get built assuming multi-tenant webhook routing already works.
- **RBAC granularity mismatch.** The spec's agent framework implies fine-grained, per-action permission checks; the existing role model is 3 flat roles with `requireRole()` enforced in only a handful of routes. Building risk-tiered agent permissions on top of this thin foundation either means extending the role model significantly first, or building agent permissions as a genuinely separate authorization layer that doesn't route through `requireRole()` at all — a design decision the spec doesn't resolve on its own.

## 10. Automation Opportunities

Concrete, low-risk opportunities given what already exists:

- **Feed `leadScoring.js`'s output directly into the Lead Intelligence Engine's `score`/`confidence`/`explanation` fields** — the computation, weighting, and tenant-configurability already exist; this is a mapping/renaming exercise, not new logic.
- **Promote `smartTriage.js` from WhatsApp-only, opt-in, to the formal Intake/Qualification agent** — its "match confidently or escalate, never guess" logic is already correct; it just needs a Tool Registry wrapper and channel-agnostic framing (it currently hardcodes WhatsApp sends).
- **Extend `cockpit.js`'s Next Best Action endpoint into the spec's general-purpose engine** by feeding it `lead360.js`'s cross-module alerts (fees/documents/visa) in addition to its current communication-only context — the two services already compute complementary data (`lead360.js` has the fee/document alerts `cockpit.js` currently lacks) and are not yet connected to each other.
- **Wire `documents.js`'s existing `document.rejected` trigger and `journey.js`'s visa-checklist cross-referencing into a new Document Agent** — the deterministic "what's missing" logic in `journey.js`'s `GET /visa/:id/checklist` is already exactly the kind of check a Document Agent needs to run; it just needs agent framing and a trigger to run proactively rather than only on-demand.
- **Wire `fees.js`'s existing auto-reminder-on-due-date and auto-receipt-on-paid logic into the Payment/Commitment Agent** — `reminderForFee()` and `generateReceipt()` are already fully automatic today; formalizing them as agent actions with an audit trail is mostly a wrapping exercise.
- **Use `engagementTrend.js`'s `cooling`/`cold` classification as the trigger condition for the new Lead Recovery Agent** — the detection signal already exists and is already computed on-demand by `cockpit.js`; it just isn't hooked to any recovery *action* today.
- **Reuse the `lead.created`/`lead.stage_changed`/`document.rejected`/`offer.given`/`fee.paid` event vocabulary as the first five entries in the new orchestrator's event catalog** — these are already fired from the correct call sites across `leads.js`, `documents.js`, `cockpit.js`, `leadAdsWebhook.js`; extending the vocabulary (adding `payment.overdue`, `document.expiring`, etc.) is additive.
- **`predictions.js`'s college-fit logic is fully built but disconnected** — wiring it into `lead360.js`'s snapshot or the Counselling Agent's context is a straightforward integration, not new development.

## 11. Risks

- **Data migration risk — 785 live leads' existing `stage` values.** Any new lifecycle-status column must either (a) run a one-time backfill mapping current free-text `stage` values (`New`, `Contacted`, `Counseling`, `Admission`, `Closed`, `Lost`, plus whatever tenant-custom `pipeline_stages` names exist) into the new enum, with an explicit fallback bucket for values that don't cleanly map, or (b) run the new lifecycle status *alongside* the old `stage` column indefinitely rather than replacing it — the former is cleaner long-term but riskier to get wrong against real production data; the latter is safer short-term but perpetuates the dual-source-of-truth problem in §2.
- **Backward-compatibility risk — the mobile app already calls the existing automation/AI/leads endpoints in production.** `GET/POST/PATCH /automations`, `GET/POST/PATCH /leads`, `POST /ai/analyze-lead/:id`, and every `cockpit.js` route are live and called by the shipped Flutter app (confirmed via `mobile/lib/services/api_service.dart` method inventory referenced in `ARCHITECTURE_MAP.md`, and directly via `automations_screen.dart`/`lead_detail_screen.dart`'s call sites read in this audit). None of these can be renamed, restructured, or have their response shape changed without a coordinated mobile-app release — any new orchestrator must add new endpoints/fields rather than mutate these in place, at least until a versioned API strategy is decided.
- **Scope risk — the spec describes a large, multi-layer system (10 agents, tool registry, orchestrator, dashboard, scheduler) against a single-developer-maintained, no-test-suite, no-staging-environment production app** (`backend/package.json`'s test script is the unconfigured `npm init` default; no CI test gate found; per the earlier `TECH_DEBT.md`, every push to `main` deploys straight to the live Render service serving real tenants). Building the full spec in one pass against this deployment posture is itself a risk; recommend the new orchestrator and agent framework ship behind a feature flag / dry-run mode initially, and that a minimal test harness exists before any agent gets HIGH-risk-tier write permissions.
- **Webhook forgery risk, now formally documented (§6).** Until `X-Hub-Signature-256` validation is added to `whatsappWebhook.js` and `leadAdsWebhook.js`, any new agent that treats inbound WhatsApp messages or Lead Ads submissions as a trusted autonomous trigger is building on an unauthenticated input — this should be fixed before, not after, an agent is given autonomy to act on these events without human review.
- **No idempotency risk compounds with autonomous agents specifically.** Today, `fireEvent()`'s lack of idempotency is a minor annoyance (a duplicate reminder, at worst). Once agents can take HIGH-risk actions (charge a payment, send a legally-relevant document, message a lead), the same lack of idempotency becomes a correctness/trust risk, not a cosmetic one — this should be treated as a blocking prerequisite for any HIGH-risk-tier agent action, not a nice-to-have.
- **RLS false-security risk carries forward unchanged.** As documented in the pre-existing `SCHEMA_SNAPSHOT.md`/`TECH_DEBT.md` and re-confirmed by this audit's reading of `db.js`, RLS is enabled-but-policy-less and fully bypassed by the connecting role. Anyone reading the Supabase dashboard and seeing "RLS enabled" on 54 tables could reasonably assume tenant isolation has a second, independent enforcement layer — it does not. Any new agent-driven write path inherits this exact same single-point-of-failure (`WHERE tenant_id = ?` discipline in the code, nothing else).

## 12. Recommended Phase 2 starting point

Start the Domain Model phase with **the lead lifecycle reconciliation, not the agent framework** — every other layer (Tool Registry, orchestrator, agents) needs a stable state model underneath it, and building agents against today's unenforced free-text `stage` column means re-doing that work once the state machine lands. Concretely:

1. Introduce a new, separate, enum-enforced column (e.g., `leads.lifecycle_status`) rather than overwriting `leads.stage` in place — write a one-time backfill migration mapping the 6 known current values (plus an explicit `UNMAPPED`/manual-review bucket for any tenant-custom `pipeline_stages` names that don't cleanly correspond) — this avoids breaking the mobile app's existing stage-filter UI (which reads `pipeline_stages.name`, unrelated to the new column) while giving the new state machine something real to enforce transitions on.
2. Add transition-validation logic (which `lifecycle_status` values a given current value may legally move to) as a small, new, additive service — do not bolt this onto `leads.js`'s existing PATCH handler without first confirming every other write path that sets `stage`/`lifecycle_status` (`leadsExcelV2.js`, `leadAdsWebhook.js`, `students.js`, capture forms) is inventoried and updated in the same pass, since a transition-validator that only some code paths respect is worse than no validator.
3. In parallel (these don't block each other), stand up the **Tool Registry** as a thin wrapper around the already-real, already-working service calls in §7 (`sendWhatsAppMessage`, `sendEmail`, `generateJson`, fee/document/reminder writes) — this is genuinely additive and low-risk because the underlying calls already exist and already work; the registry just needs to interpose permission/schema/audit-logging before delegating to them.
4. Defer the durable orchestrator (idempotency + retry/backoff + dead-letter) until after the Tool Registry exists, since the orchestrator's job is to safely call registered tools — building it first, against today's un-registered direct function calls, means redoing its integration surface once the registry lands.
5. Fix the two unauthenticated webhooks (§6) as a fast, isolated, high-value first PR — it's independent of everything else above, closes a real security gap, and is a good low-risk way to validate the audit's security findings against actual production behavior before larger changes begin.
